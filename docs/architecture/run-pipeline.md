# Конвейер запуска задачи

Кратко: задача уходит в Claude через очередь проекта, Claude работает в отдельной рабочей копии git, результат попадает в статус и в Telegram. Функции: runTask (`docs/functions/server/worker/runTask.md:L13#Алгоритм`).

## Этапы запуска
1. Пользователь запускает задачу: API, бот или кнопка. Всё сходится в `server/src/services/runs/startTask.js:L5-15#startTask`.
2. Задача ставится в очередь проекта `server/src/worker/queue/enqueue.js:L6-17#enqueue`. Подробнее: enqueue (`docs/functions/server/worker/enqueue.md:L3#Назначение`).
3. Воркер готовит клон проекта prepareWorkdir (`docs/functions/server/worker/prepareWorkdir.md:L13#Алгоритм`).
4. Запускается `claude` с инструментами из claudeTools (`docs/functions/server/worker/claudeTools.md:L13#Алгоритм`) через runClaude (`docs/functions/server/worker/runClaude.md:L13#Алгоритм`).
5. По итогу выбирается исход (таблица ниже) и уведомление уходит в Telegram.

## Исходы запуска
Порядок проверок важен: первое совпавшее условие определяет статус. Таблица со ссылками на строки: runTask (`docs/functions/server/worker/runTask.md:L13#Алгоритм`).

**Лимит подписки** определяется только по упавшему запуску и только по тексту ошибки (итог запуска, stderr): `server/src/worker/limits.js:L13-16#isLimitError`. Весь вывод Claude для этого не проверяется: в нём всё, что он прочитал и написал, и слова «rate limit» или «лимит» встречаются в обычном коде, из-за чего успешный запуск принимался за лимит, коммиты терялись, а задача возвращалась в «Готово к работе». Регрессия закрыта сквозным тестом `server/test/runTask.e2e.test.js` (подставной `claude`, настоящий git).

**Имя автора git.** Перед подготовкой клона воркер задаёт `user.name` и `user.email` в репозитории проекта, если их нет нигде: `server/src/worker/worktree.js:L7-11#ensureGitIdentity`. Без этого `git commit` и `git rebase` на свежем сервере падают с «Committer identity unknown».

**Автопроверка** (перед «На проверке»): после пуша воркер запускает `npm run test` и `npm run lint`, если они объявлены в `package.json` проекта. Зависимости ставятся один раз в рабочую копию. Результат пишется системным комментарием «Автопроверка: …», хвосты вывода — в лог запуска, а в уведомлении есть строка с итогом. Статус от результата не меняется: решение за владельцем. Код: `server/src/worker/verify/runChecks.js:L8-22#runChecks`, вызов в `server/src/worker/outcome.js:L64@runChecks(wt)`. Тесты: `server/test/verify.test.js:L13@describe('автопроверка`.

## Рабочая копия
Отдельных веток на задачу нет. Claude работает прямо в клоне проекта `REPOS_DIR/<slug>` (без отдельного worktree): так `node_modules` живут между запусками. Запуски проекта идут по очереди, поэтому клон занят одной задачей; перед запуском незакоммиченные остатки стираются. Локальная ветка `task/<id>` нужна только на время запуска. Куда уходит результат, задаёт флажок проекта «Пушить сразу в ПРОД» (`commitToBase`) и поле «Ветка UAT» (`uatBranch`, по умолчанию `uat`), настройки читает `server/src/services/projects/baseBranch.js:L7-14#branchSettings`:
- **Выключен (по умолчанию):** результат уходит в ветку UAT, а при приёмке задачи вливается в основную (см. ниже). Если ветки UAT нет в origin, `prepareWorkdir` создаёт её от основной.
- **Включён:** результат уходит прямо в основную ветку, без проверки в UAT.
- В обоих случаях воркер перекладывает коммиты поверх свежей целевой ветки (`git rebase`) и пушит в неё: `server/src/worker/publish.js:L27-48#publishToBase`. Если её успели обновить между вытягиванием и пушем, попытка повторяется один раз. Хеши коммитов запуска копятся в `Task.commits`. При конфликте или отклонённом пуше (защищённая ветка, нет прав) целевая ветка не меняется, работа сохраняется в `task/<id>` на GitHub (принудительный пуш в эту ветку: она только наша), статус «Ошибка» с причиной, дальше работает кнопка «Попросить Claude исправить». Автопроверка идёт уже после отправки и статус не меняет. В карточке полем «Ветка» показана целевая ветка, а diff строится по коммитам запуска (`Task.diffRange`): `server/src/services/diff.js:L8-15#taskDiff`.
- Пока Claude ждёт ответа на вопрос, незавершённая работа лежит в `task/<id>` на GitHub; после публикации результата ветка удаляется.
- Claude сам не пушит: он только коммитит в локальную ветку. Продолжение после вопроса берёт ветку из origin: prepareWorkdir (`docs/functions/server/worker/prepareWorkdir.md:L13#Алгоритм`).

### Приёмка: из UAT в основную ветку
Кнопка «Принять результат» (интерфейс идёт через `PATCH /api/tasks/:id`, Telegram через callback) вызывает `server/src/services/runs/acceptTask.js:L9-29#acceptTask`. Если результат лежит не в основной ветке, коммиты из `Task.commits` переносятся в неё через `git cherry-pick` во временной копии, а не в клоне проекта (он может быть занят запуском): `server/src/worker/promote.js:L12-40#promoteToBase`. Так принимать задачи можно в любом порядке, а чужие коммиты из UAT в основную не попадают. Если основную ветку успели обновить, попытка повторяется один раз. При конфликте или отказе GitHub задача остаётся «На проверке», причина показывается в ответе. Если результат уже в основной ветке (проект пушит сразу в ПРОД), меняется только статус.
Ограничение: после переноса UAT и основная ветка расходятся по хешам (cherry-pick создаёт новые коммиты), и ветку UAT нужно время от времени выравнивать с основной вручную.

## Аккаунт Claude
Если на аккаунте Claude, залогиненном на сервере, закончился лимит, запуски можно переключить на другой аккаунт
без доступа к серверу: карточка «Claude» в «Настройках» (`client/src/components/ClaudeSettings.jsx`) принимает
метку, тип (API-ключ или долгоживущий токен `claude setup-token`) и сам ключ. У Anthropic нет общего «whoami» ни
для ключа, ни для токена, поэтому в отличие от GitHub он не проверяется запросом к сети — только сохраняется.
Хранение зеркалит GitHub: токен зашифрован в `Settings` (`server/src/services/claude/settings.js`), маршруты
`GET/PUT/DELETE /api/claude` (`server/src/routes/claude.js`). Подстановка в окружение процесса `claude`:
`server/src/worker/env.js:L37-44#claudeEnv` — без сохранённого аккаунта окружение не меняется (аккаунт сервера),
с сохранённым подставляет `ANTHROPIC_API_KEY` или `CLAUDE_CODE_OAUTH_TOKEN` вместо значения из окружения сервера.
Используется в `server/src/worker/runTask.js:L50@...claudeEnv()`, поэтому новый аккаунт действует для всех задач
сразу со следующего запуска. Отключение возвращает воркер к аккаунту сервера.

### Вход через подписку Pro/Max (без терминала)
Токен подписки обычно получают командой `claude setup-token` в терминале. Чтобы не заходить на сервер, кнопка «Войти через подписку»
(`client/src/components/claude/ClaudeLogin.jsx`) проводит этот вход через браузер:
1. `POST /api/claude/login` (`server/src/routes/claude/startClaudeLogin.js`) запускает `claude setup-token` в псевдотерминале
   (утилита `script` из util-linux, новых зависимостей нет) и отдаёт ссылку из вывода: `server/src/services/claude/login/session.js`.
   Терминал широкий (500 колонок), поэтому ссылка и токен не переносятся; вывод разбирает `login/terminal.js`.
2. Владелец открывает ссылку (с телефона тоже), входит в аккаунт с подпиской и копирует код со страницы.
3. `POST /api/claude/login/code` передаёт код в команду, через 300 мс отдельной записью шлёт Enter (иначе терминал принимает код с Enter
   за вставку и не отправляет), ждёт до 60 с токен вида `sk-ant-oat…` и сохраняет его как тип `oauth_token`
   (`login/index.js`). Токен наружу не отдаётся и в логи не пишется.
Команда идёт без ключей из окружения сервера и с отдельной временной папкой `CLAUDE_CONFIG_DIR`, поэтому не трогает вход, сохранённый на сервере.
Одновременно идёт один вход, он закрывается сам через 10 минут, по отмене или новому входу; процесс и временная папка убираются.
Если `script` нет на сервере, ответ 503 с подсказкой; токен можно ввести вручную.

## Очередь
Очередь в памяти, по ключу проекта. Задачи одного репозитория идут по очереди. Ждущие запуски помечены в задаче (`queued`), поэтому после перезапуска они возвращаются в очередь: `server/src/services/runs/recoverRuns.js:L10@export async function recoverRuns`. Детали: enqueue (`docs/functions/server/worker/enqueue.md:L3#Назначение`).

## Отмена и таймаут
Оба случая отправляют SIGTERM через реестр процессов: `server/src/worker/processes/stopRun.js:L6-18#stopRun`. Причина (`cancelled` или `timeout`) определяет исход. Если процесс не завершился за 10 секунд, идёт SIGKILL (`server/src/worker/processes/config.js:L2@KILL_AFTER_MS`), см. stopRun (`docs/functions/server/worker/stopRun.md:L13#Алгоритм`).

## Здоровье
Публичный `/api/health` отвечает 200 или 503 и показывает по каждому сервису (база, Claude Code, хранилище, Telegram) признак «в норме». Проверки кэшируются на 30 секунд: `server/src/services/health/getChecks.js:L11-28#getChecks`. Подробности для владельца (очередь по проектам, запуски, зависшие задачи «в работе» без процесса) собирает `server/src/services/health/details.js:L9-36#getDetails` и показывает блок «Состояние» в «Настройках».

## Состояния задачи
Таблица статусов и переходов: `shared/statuses.js:L24-32#TRANSITIONS`. Ручные переходы проверяет `server/src/routes/tasks/patchTask.js:L6-13#patchTask` (подробно (`docs/functions/server/routes/patchTask.md:L14#Алгоритм`)).

Инструкция запуска `/implement-task` лежит в репозитории трекера (`.claude/skills/implement-task`), а задача идёт в репозитории проекта. Поэтому перед запуском Claude воркер копирует её в рабочую копию (`server/src/worker/installSkill.js`), если у проекта своей нет, и исключает из git: в коммит она не попадает. Без неё Claude не находил команду, работал без плана и не делал коммит. Процесс claude запускается с закрытым stdin.
